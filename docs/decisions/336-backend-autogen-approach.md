## 結論(推奨)

**A(宣言的なサーバー機能)で始める。B(AI がコードを書く)は今は作らず、C(併用)へ進むかは、A を出した後に「A で表せない依頼」を測ってから決める。**

- #269〜#273 の 5 本は、**すべて A で表せる**(下の表)。B が要る具体的な需要は、今のところ見つかっていない。
- A は今の DSL と同じ作り(閉じた enum・`additionalProperties:false`・Go の `Validate()`・JSON Patch での編集)なので、AI の生成・検証・版の管理・OS をまたぐ扱い(#351)を今の仕組みのまま伸ばせる。
- 大事な気づき: 5 本のうち**本当に「きっかけ → 処理」が要るのは #269(と #270 の一部)だけ**。#271・#272・#273 は、appconfig が書き込み・読み取りの時にその場で確かめる**データの決まり(権限・一意)**で、非同期の実行基盤は要らない。A の語彙は「データの決まり」「読み取りの絞り込み」「サーバーの自動の動き」の 3 種に分けて考える。
- B は、隔離(#337)・費用(#338)・脅威(#339)・審査の説明(#349)の作り込みがそれぞれ一段重くなり、2 人のチームの M4 の見積もり(設計 2 週 + 実装 6〜8 週・[ロードマップ](../roadmap/roadmap-m1-m6.md))に入らない。#344 は「C に決まった場合だけ」のまま保留にする。
- 「9 割を A で賄える」は**推測**。A を出した後、生成で断った依頼を分類して測る(段階 4)。足りない分は、まず A の語彙を足して埋める。

## 選択肢

| 案 | 中身 | 良い | 悪い |
|---|---|---|---|
| **A. 宣言だけ(推奨)** | DSL に「データの決まり」と「きっかけ → 条件 → 処理」を、運営が用意した閉じた語彙で書く。共通のエンジン(appconfig と実行基盤)が実行する | 安全・検証しやすい・費用が読める・今の DSL と同じ作り・OS に依らない | 表せる処理が語彙の分だけ |
| B. AI がコードを書く | アプリごとに関数(JS / WASM / Go など)を生成し、サンドボックスで動かす | 何でも書ける | 悪用・費用・デバッグ・審査の説明が難しい。隔離の作り込みが大きい |
| C. 併用 | A を既定にし、A で表せないものだけ B(Pro・人の確認つき) | 段階的に広げられる | 2 つの仕組みを持ち、B の重さは結局すべて払う |

## 評価の表

◎ よい / ○ 足りる / △ 作り込みが要る / × 難しい。C は「B の部分」の重さをそのまま持つので、ほぼ B と同じ評価になる(A の部分は A と同じ)。

| 観点 | A. 宣言 | B. コード | C. 併用 |
|---|---|---|---|
| 安全・悪用(脅威は #339) | ◎ できることが語彙で閉じる。宛先・頻度・書ける範囲を**エンジンが**強制し、生成の段(検証)と実行の段(上限)の両方で止められる | × 生成されたコードが何をするかを事前に保証できない。静的な検査は補助にしかならず、守りは実行時の隔離と上限に頼る | △ B の部分は B と同じ。B を Pro・人の確認つきにしても、確認する人の負担が残る |
| 費用と予測のしやすさ(#338) | ◎ 処理 1 回あたりの原価(書き込み・プッシュ・読み取り)を語彙ごとに決められ、上限も単位で数えられる | △ CPU 時間・メモリ・実行回数が依頼しだいで変わる。サンドボックスの基盤自体の費用も足される(価格は要確認) | △ 2 本立ての計量 |
| 隔離・マルチテナント(#337) | ○ 触れるのは「そのアプリの entity」だけ、とエンジンが API の 1 か所で強制できる(今の `recordSet` / 参加者の判定の延長)。アプリごとのキュー・同時実行の上限は要る | × 外向きの通信・ファイル・CPU / メモリ・時間・資格情報の分離をすべて作り込み、破れていないかの試験も要る | × B と同じ |
| 審査 2.5.2 / 4.7(#349) | ◎ 端末に送るのは DSL と通知だけで、コードは端末にもサーバーにも生成しない。今の審査メモの説明(「記録帳の設定」)と同じ線で書ける | △ サーバーで動くので 2.5.2 にはかかりにくい見込み(**推測**)。ただし「AI がプログラムを書いて動かす」は、ストアの言い方の方針([wording.md](../store/wording.md))が避けている言い方そのもので、4.7・4.2.6 の説明が難しくなる | △ B の部分を説明に含めるかどうかで変わる |
| 信頼性・非エンジニアのデバッグ | ◎ 各ルールから人が読める説明を機械的に作れる(「誰かが出欠をつけたら、作成者に通知」)。実行の記録も「どのルールが・何をした・なぜ失敗した」を同じ言葉で出せる(#347) | × 失敗の理由がコードの中にあり、作成者には読めない。直すのも AI 任せになる | △ |
| AI の生成の正確さ | ◎ 構造化出力 + スキーマ + 意味の検証 + 模擬の実行(#343)。Expr の導入(計算 5/5)と同じやり方が使える | △ 文法は通っても意図どおりかの確認が難しい。確かめるにはサンドボックスで動かす試験が要る | △ |

## #269〜#273 は A で表せるか

「種類」は、次の章の 3 種(**データの決まり** = appconfig がその場で確かめる / **絞り込み** = 読み取りの条件 / **自動の動き** = きっかけで非同期に動く)のどれで表すか。

| Issue | 需要 | A で表せるか | 種類 | 書き方の例(案) | 残る注意 |
|---|---|---|---|---|---|
| [#269](https://github.com/jphacks/kz_2601/issues/269) 他人の行動でプッシュ | 新着メッセージ・出欠がついたら通知 | **表せる** | 自動の動き | きっかけ「`messages` が作られた」→ 処理「参加者全員(書いた本人を除く)に通知」。出欠は「`rsvps` が作られた」→「親の予定を作った人に通知」 | 端末トークンの登録・APNs の送信・通知の受け取り設定は #269 自体で作る(新しい iOS の版が要る)。宛先と頻度の制限は #339 |
| [#270](https://github.com/jphacks/kz_2601/issues/270) フォローした人のタイムライン | フォローした人の投稿だけ | **表せる(条件つき)** | 絞り込み(+ 共通の仕組み) | フォローを全アプリ共通の関係として appconfig に持ち、部品の filter に「作者がフォロー一覧に含まれる」を足す | 自動の動きではない。フォローが多い時の読み取り方(Firestore の `in` の件数の上限・要確認)で、読み取り時に絞るか、投稿時に配る(自動の動き)かを #341 で決める。配る方は費用が大きい |
| [#271](https://github.com/jphacks/kz_2601/issues/271) 1 対 1・グループ宛て | 宛先の人だけが読める・既読 | **表せる** | データの決まり(読み取りの権限)+ 既存の `marks` | entity に「宛先の field」を宣言し、読めるのは作者と宛先だけ。既読は印(`marks`)。新着の通知は #269 の宛先「宛先の field の人」 | SSE の通知とプッシュの本文で、宛先以外に中身を出さないこと(#337 の試験に入れる) |
| [#272](https://github.com/jphacks/kz_2601/issues/272) 役割と権限 | 店長だけが確定・削除できる | **表せる** | データの決まり(書き込みの権限) | 参加者表に役割(owner / member、必要なら admin)。field に「変えられる役割」、button に「見える役割」 | 役割を誰がどう付けるかの UI(iOS)。役割の種類を自由に作るのは語彙の外(固定の数個にする) |
| [#273](https://github.com/jphacks/kz_2601/issues/273) 一意・重複防止 | 同じ時間に 2 人予約しない・1 人 1 回答 | **表せる(一部は語彙を足す)** | データの決まり(一意) | entity に「この field の組は一意」(例: 開始時刻、または 予定 + `$author`)。appconfig が作成時にトランザクションで確かめて 409 | 「値が同じ」は表せるが、「時間帯が重なる」(10:00〜11:00 と 10:30〜11:30)と「定員 N 人まで」は一意では表せない。**`重ならない`・`定員` の語彙を足せば A のまま表せる**(B は要らない) |

**まとめ**: 5 本とも A で表せる。#273 の「重なり」「定員」だけ、最初の語彙に入れるか後で足すかを決める。

**A で表せないもの(参考)**: 外部のサービスとの任意の連携(#348 は許可リストの語彙として A に入れる案)、シフトの自動の割り当てのような最適化、繰り返し・状態を持つ長い手順、レコードを AI で要約するような重い処理。どれも、危ないか、語彙として後から足せる(例: 「AI で要約」を上限つきの処理として用意する)。B でしか解けないと分かったものは、まだ無い。

## 最小の A の語彙(案)

実装はしない。#340 でスキーマにする時の出発点。名前・形はすべて仮。

### 1. データの決まり(appconfig が書き込み・読み取りの時にその場で確かめる)

| 宣言 | 置き場(仮) | 意味 | 対応 |
|---|---|---|---|
| 一意 | `entity.unique: [[field, …]]` | その field の組が同じレコードを 2 つ作れない(409) | #273 |
| 重ならない・定員(後で) | `entity.noOverlap` / `entity.capacity` | 時間帯の重なり・同じ値のレコード数の上限 | #273 の残り |
| 役割 | 参加者表の `role`(owner / member / admin) | 作成者 = owner | #272 |
| 書き込みの権限 | `field.editableBy`・`entity.deletableBy` | 役割で絞る(今の `entity.edit` の延長) | #272 |
| 見える役割 | button などの `visibleTo` | iOS は隠し、appconfig は書き込みで確かめる(隠すだけに頼らない) | #272 |
| 宛先 | `entity.audience: {field}` | 読めるのは作者と、その field に入った人だけ | #271 |

### 2. 絞り込み(読み取り)

| 宣言 | 意味 | 対応 |
|---|---|---|
| filter の値 `{"myFollows": true}`(`$author` と組む) | 作者が自分のフォロー一覧に入っている | #270 |

今の filter に値の種類を 1 つ足すだけ。フォローの関係そのものは全アプリ共通の仕組み(アプリの宣言ではない)。

### 3. 自動の動き(きっかけ → 条件 → 処理)

```json
{
  "serverRules": [
    {
      "id": "notify_rsvp",
      "on": { "record": "created", "entity": "rsvps" },
      "if": { "op": "eq", "args": [{ "ref": "answer" }, "yes"] },
      "do": [
        { "notify": { "to": { "authorOf": "event" }, "title": "出欠", "body": "{$author}さんが参加にしました" } }
      ]
    }
  ]
}
```

| 部分 | 最初に入れる | 後で(需要を見て) | 入れない |
|---|---|---|---|
| きっかけ | レコードの作成・更新(更新は「この field が変わった時」に絞れる)、時刻(毎日 HH:MM・毎週 曜日・毎月 日。作成者のタイムゾーン) | レコードの削除 | 外からの呼び出し(Webhook)、他のアプリのレコード |
| 条件 | Expr の部分集合: きっかけのレコード(`ref`)と、更新なら前の値。比較・論理・算術・日付(`today` はアプリのタイムゾーンで評価) | `agg`(集計は読み取りが増えるので費用の単位を決めてから) | 端末にしか無い値、他のアプリ |
| 処理: 通知 | 宛先は閉じた種類だけ: 参加者全員・作成者(owner)・このレコードの作者・ref 先のレコードの作者・宛先の field の人・役割。本文は決まった枠 + レコードの値の差し込み(長さの上限)。押すとそのアプリを開く | 通知の画面の指定 | 任意の uid・メールアドレス・電話・外部の宛先。参加者でない人 |
| 処理: レコードを書く | 同じアプリの entity にレコードを作る・きっかけのレコード / ref 先の field を更新する(値は Expr) | 条件に合う複数のレコードの更新(件数の上限つき) | 全件の削除、他のアプリ・他の人の個人の記録 |
| 処理: 集計 | 親のレコードの数の field を増やす・減らす(件数・合計) | 定期の集計のやり直し・リセット | — |
| 外部との連携 | — | 運営の許可リストの連携だけ(#348) | 任意の URL |

**エンジンが必ず守ること**(生成された宣言に何が書かれていても): 処理が触れるのはそのアプリのデータだけ、宛先は参加者だけ、処理が書いたレコードでは(最初は)次のきっかけを起こさない、1 ルールの処理の数・1 アプリのルールの数・頻度に上限。詳しい値と根拠は #337・#338・#339 で決める。

**共有アプリでどの宣言が動くか**: 共有アプリでは、参加者それぞれが自分の DSL のコピーを持つ([shared-data.md](../backend/features/shared-data.md))。共有データに対して動く宣言は、**作成者が公開した DSL(`apps_public/{appId}`)のものだけ**にする(参加者が自分のコピーを書き換えても共有データには効かない)。自分だけの記録(`private`)に対する宣言は、その人の DSL のものが、その人のデータだけに効く。この線引きは #337 で確定する。

## 実行の場所と失敗の扱い

### 実行の場所(案)

| 種類 | 場所 | 理由 |

| データの決まり(一意・権限・宛先) | **appconfig の中** | 書き込み・読み取りの要求の中で、その場で 403 / 409 を返す。今の `ownRecord` / 参加者の判定と同じ場所 |
| 自動の動き(きっかけ・時刻) | **新しいサービス `runner`(推奨)** か、appconfig の中の別の入口 | 下の比較 |

| 案 | 良い | 悪い |
|---|---|---|
| **`runner` を足す(推奨)** | 背景で動き、再試行・急な増え方があるので**スケールの特性が違う**([00_decisions.md](../00_decisions.md) の「増やすのはスケール特性が違う時」に当たる)。appconfig の応答の速さに影響しない。資格情報を分けやすい(#337) | サービスが 3 つになる(デプロイ・監視・設定が増える) |
| appconfig の中の別の入口 | 足すものが少ない。最初は速い | 背景の負荷が利用者の要求と同じインスタンスに乗る。後で分ける時に作り直し |

きっかけの拾い方は #341 で決めるが、書き込みが全部 appconfig を通るので、**書き込みと同じトランザクションで outbox に積む**形が素直(Firestore のトリガーより、どの要求から来たかを確実に持てる)。

### 失敗した時・遅い時(案)

| 場面 | 扱い |
|---|---|
| 同じきっかけが 2 回届く | 「きっかけの ID + ルールの ID」で 1 回しか処理しない(冪等) |
| 一時的な失敗 | 回数の上限つきで間を空けて再試行。上限を超えたら止めて記録 |
| 遅い | 処理ごとに時間の上限。通知は「数十秒以内に届けば十分」を目標にし、遅れても順序は保証しない |
| 上限に達した・止められた | 実行しない(後でまとめて実行もしない)。作成者に理由を出す |
| 作成者への見せ方 | 「自動の動き」の一覧と直近の結果を、やさしい言葉で(#347)。失敗が続いたらチャットで直し方を提案 |
| 処理が処理を呼ぶ | 最初は「処理が書いたレコードではきっかけを起こさない」。連鎖が要る需要が出たら深さの上限つきで |

## #337・#338・#339 に答えてほしいこと

### #337 隔離とマルチテナント

- 共有アプリで動く宣言を「作成者の公開 DSL だけ」にする線引きでよいか。作成者が退会・外された時に、その共有アプリの自動の動きをどうするか(止める / 残す)。
- `runner` の資格情報: 共通のサービスアカウントで、触れる範囲をエンジンの 1 か所で絞る形でよいか。
- 1 つのアプリの暴走が他に響かない仕組み(アプリごとのキュー・同時実行の上限)の単位。
- 隔離が破れていないことの試験(別のアプリ・参加者でない人・宛先でない人にデータが届かない)。SSE とプッシュの本文も対象にする。
- stg と prod が Firestore を共有している今、定期処理と outbox をどちらの環境で動かすか(#288 の分離の進み具合)。

### #338 費用モデル

- 数える単位: ルールの実行・書き込み・通知・(後で)集計の読み取り。語彙ごとの原価。
- 無料 / Pro の量と、超えた時に止める(遅らせない)でよいか。
- 共有アプリの費用を作成者に付けるか、きっかけを起こした参加者に付けるか。
- 全体の予算の遮断(今の `RATE_LIMIT_GLOBAL_DAILY` と同じ考え方)を自動の動きにも置くか。使われていないアプリの定期処理を止めるまでの期間。

### #339 悪用と脅威

- 生成の段で止めるもの(宛先・本文・頻度の宣言の検証)と、実行の段で止めるもの(上限・停止)の分け方。
- 通知の本文の差し込みの制限(長さ・リンクを入れない等)と、宛先・頻度の上限の値。
- 指示文に紛れ込ませた命令(「全員のレコードを消して」)を、語彙に全件の削除を入れないことで防ぐ方針でよいか。
- 通報(#321)から自動の停止(#346)までの流れ。通報の多いアプリを自動で一時停止するか。
- 試験ケースの一覧(悪い依頼・悪い宣言)を ai-eval とテストのどちらに置くか。
