## 結論(推奨)

**公開リポジトリの Issue には、フィードバックの原文も個人情報も絶対に載せない。載せるのは、人が承認した「書き直した要約と再現の手順」だけ。そのために、下書きは非公開の場所に置き、人が承認してから要約だけを公開の Issue にする。**

- **同意の版を上げ、「改善のために AI(Anthropic・米国)が読む」を同意文に足す**。旧版(`feedback-2026-11`)で送られたフィードバックは、AI に回さない(版の許可リストで機械的に落とす)。今の同意文の「第三者には渡しません」は、AI に回すなら書き換えが要る。
- **伏せ字は LLM に送る前、取り込みの保存の時に**(#365 の段 1)。決まった形の検出(メール・電話・URL・トークン・番号・住所の形など)を必ず通し、名前などの形の無いものは Google の機密データの検出(Sensitive Data Protection・要確認)を補助に使う。**生の本文を、伏せ字のために Anthropic に送ることはしない**。
- **LLM に渡すのは伏せ字済みの本文だけ**。スクショは渡さない、DSL は構造(部品の種類)だけ、クラッシュは件数と種類と版だけ(#366 の「決めてほしいこと 2」と同じ)。
- **伏せ字・検査が失敗したら止まる(fail closed)**。そのフィードバックは自動の段に流さず、人の週の振り分け([β の品質ゲート 5 章](../release/beta-quality-gate.md#5-フィードバックの振り分けm6-の手作業版))に残す。
- **派生物の保存期間は元より長くしない**。取り込みの写し・振り分けの結果・下書きは、元のフィードバック(180 日)と同時かそれより早く消え、アカウントの削除(#119)でも消える。そのために派生物にも `uid` を(LLM に渡さない項目として)持たせ、`PurgeAccount` の対象に足す。
- **公開の Issue は消せない前提で扱う**。投稿した瞬間に watch している人へ通知のメールが届き、取り消せない。だから「出してから直す」ではなく「出す前に人が見る」にする。これは #365 の段 3(下書きを `needs-approval` の公開 Issue として出す)を変える提案なので、#365 と一緒に決める。
- **ポリシー・同意文・プライバシーの表示を直してから、ループを始める**(#368 の開始の条件にする)。

### #319 で同意済みのこと・足りないこと

| ループでしたいこと | 今の同意(`feedback-2026-11`)で足りるか |
|---|---|
| 運営者が読む・Firestore に保存・180 日で消す | 足りる |
| 伏せ字済みの本文を **Anthropic(米国)** の LLM に送って振り分ける | **足りない**。文面は「運営者が読みます」「第三者には渡しません」。ポリシー §1.3 の AI の同意は「アプリを作る・直す・相談する時に限り」で、目的が違う。ポリシー §6 は「AI に送る情報や送り先を変える場合は、改めて同意をいただきます」と約束している |
| 書き直した要約を公開リポジトリの Issue に載せる | 個人を特定できない要約なら個人情報ではない、という扱いの見込み(**要確認**)。ただし「送った内容が公開の場で話題になる」ことは同意文に書くのが誠実 |
| 原文・個人情報を公開の Issue に載せる | **どの同意でもしない**(載せない、と決める) |
| Google の機密データの検出に通す | Google は既存の委託先(§2)。同意文の「Google Cloud に保存」の範囲内の見込み(**要確認**) |

法令の論点(**要確認**・専門家に): 利用目的の変更(個人情報保護法 17・18 条)と、外国にある委託先への提供(28 条)。アプリを作る時の AI の同意で Anthropic の説明は済んでいるが、フィードバックは目的が違うので、新しい同意で目的と送り先を書くのを推奨する。

### 同意文の案(版を上げる。例: `feedback-2027-01`)

> 送った内容(本文と、オンにした添付)は、Tailor It の不具合を直し、改善するために運営者が読みます。また、**本文は名前・連絡先などを伏せ字にしてから、内容の整理のために AI(Anthropic, PBC・米国)に送ります**(スクリーンショットとアプリの設計の文字は AI に送りません)。改善の作業の記録(GitHub の公開のページ)には、個人を特定できないように書き直した要約だけを載せます。Google Cloud(Firestore)に保存し、180 日後に消去します。アカウントを削除したときも消去します。

- 版の許可リスト(例: `LOOP_CONSENT_VERSIONS`)に入った版のフィードバックだけを段 2 に回す。サーバーが今は版の中身を確かめていないので、段 1 が必ず確かめる。
- 旧版のフィードバックは、180 日で消えるまで人の手作業の振り分けだけで扱う。
- 同意文に保存期間を出しているので、期間を変えたら版も上げる(`FeedbackConsent.retentionDays` と `store.FeedbackRetention` を揃える)。

## 公開の Issue に載せてよいもの

> **最重要: 公開リポジトリの Issue・コメント・PR・コミット・Actions のログに、フィードバックの原文・スクショ・DSL の文字列・uid(ハッシュを含む)・`feedbackId`・メール・名前などを載せない。** 公開の Issue は作った瞬間に通知のメールが届き、検索エンジン・アーカイブに写り、編集の履歴も残る。消しても取り戻せない。

許可リスト(これ以外は検査器 2 で落とす):

| 載せてよい | 載せない |
|---|---|
| 人が書き直した症状(「写真を追加すると落ちる」の粒度) | 原文の引用・言い回しの長い一致(#366 の検査器 2) |
| 一般化した再現の手順(部品の種類・操作。例: 「一覧の部品に 50 件以上ある時に並べ替え」) | アプリ名・画面の文言・項目の名前・選択肢・記録の値 |
| アプリの版・ビルド番号・OS の大きい版(例: iOS 26) | 機種・言語・地域・日時の細かい値(テスターが少ない間は組み合わせで特定できる) |
| 件数(「3 件」)・入口の種類(アプリ内 / クラッシュ / レビュー) | `feedbackId`・uid・`uid_hash`・インストールの識別子 |
| Crashlytics の問題の URL(権限が無いと開けない) | スクショ・DSL・ログの抜き書き |
| 領域(生成・描画・共有・課金)・優先度の案 | 健康・お金・連絡先の具体の値 |

`feedbackId` と Issue の番号の対応は、非公開の監査ログ(#375)にだけ持つ。今の手作業の手順([β の品質ゲート 5 章](../release/beta-quality-gate.md#5-フィードバックの振り分けm6-の手作業版))は Issue に `feedbackId` を書くので、合わせて直すことを提案する(`feedbackId` 単体では個人は分からないが、公開の場に置く理由も無い)。

### 非公開の置き場所か、要約だけ公開か

下書きの段(#369)で LLM が書いた文には、伏せ字の漏れが残りうる。公開の Issue として出してから人が見る形(#365 の今の案)だと、漏れた時に取り消せない。比べたのが [選択肢 3](#選択肢-3-下書きの置き場所)。推奨は **B: 下書きは非公開、承認後に要約だけ公開**。

## 伏せ字

### どこで

```mermaid
flowchart LR
  F[(feedback/{id}<br/>原文・運営者だけ)] --> R1[伏せ字 1: 決まった形<br/>LLM を含まない]
  R1 --> R2[伏せ字 2: 機密データの検出<br/>Google・要確認]
  R2 --> Q{残りの検査<br/>失敗・多すぎ?}
  Q -->|通る| I[(loop_inbox<br/>伏せ字済み)]
  Q -->|落ちる| M[人の手作業の振り分けへ<br/>自動の段に流さない]
  I --> T[[振り分けの LLM<br/>#376]]
  T --> D[[下書き #369]]
  D --> C2{検査器 2<br/>#366 と共通}
  C2 -->|通る| P[(非公開の下書き)]
  P --> H{{人の承認 1}}
  H --> G[公開の Issue<br/>要約だけ]
```

- **LLM の前(段 1 の保存の時)に必ず伏せ字**。`loop_inbox` には伏せ字済みの文しか置かないので、後の段が原文を読むことは無い。
- **LLM の後にも検査**(検査器 2)。LLM が伏せ字の前の値を推測で書き戻す・別の言い方で個人を特定できる形にすることがあるため。
- **最後は人**。承認 1 で、要約に個人を特定できる所が無いかを見る(承認の画面に確かめる項目として出す)。

### 何を(種類と方法)

| 種類 | 方法 | 置き換え |
|---|---|---|
| メールアドレス | 決まった形 | `[メール]` |
| 電話番号(日本の固定・携帯・+81・国際) | 決まった形 | `[電話]` |
| URL・ドメイン | 決まった形 | `[URL]` |
| トークン・鍵(API キーの接頭辞・JWT・長い 16 進 / base64・`Bearer`) | 決まった形(secrets-scan と同じ規則を使う) | `[秘密]` |
| 番号(カード番号は Luhn、マイナンバー 12 桁、口座、郵便番号 `〒`・7 桁) | 決まった形 | `[番号]` |
| 住所(都道府県 + 市区町村 + 番地の形) | 決まった形 + 検出 2 | `[住所]` |
| 位置(緯度経度の形)・IP アドレス | 決まった形 | `[位置]` |
| ID(Firebase の uid の形の 28 文字・`fb_`・appId) | 決まった形 | `[ID]` |
| 人の名前(本人・他人)・`@` で始まる語 | 検出 2(Google)+ 敬称の前の語(「○○さん」)の決まった形。漏れは検査器 2 と人で拾う | `[名前]` |
| 金額 | 振り分けに金額そのものは要らない。`¥`・`円` の前の数を伏せる | `[金額]` |
| 健康(病名・体重・歩数・薬) | 形が無いので伏せ字では取り切れない。**スクショを渡さない・DSL の文字列を渡さない**ことで入口を狭め、本文の残りは検査器 2 と人 | 検出したら `[健康]` |
| DSL の自由な文字列(アプリ名・項目名・選択肢) | 伏せ字ではなく**捨てる**(構造だけを写す) | — |
| スクショ | 伏せ字ではなく**渡さない**(画像の文字の検出は確実でない) | — |

- 決まった形の規則と試験の例は公開してよい(攻撃の手順ではない)。試験の例は作った値だけを使う。
- 伏せ字は「多めに消す」向きに倒す。誤って消しすぎても振り分けの質が少し落ちるだけで、漏れより軽い。
- LLM で伏せ字をする案(原文を LLM に送って名前を探させる)は採らない。伏せ字の前の原文が Anthropic に届くことになり、伏せ字の意味が無くなるため。LLM は「出力に個人情報らしい所が残っていないか」の補助の印(`pii_suspected`)を返すだけにする(#366 の JSON の項目に足す)。

### 失敗した時

| 起きたこと | 扱い |
|---|---|
| 伏せ字の処理が落ちる・検出 2 が使えない | そのフィードバックは `loop_inbox` に入れない(fail closed)。人の手作業の振り分けに残る。監査ログ(#375)に `feedbackId` と理由だけ |
| 伏せ字の数が多すぎる(例: 本文の 3 割以上) | 自動に流さず人へ。要約しても意味が残らない |
| 振り分けの LLM が `pii_suspected: true` | その件は下書きにしない。人へ |
| 検査器 2 が下書きに個人情報の形を見つける | 下書きを捨てる。中身はログに書かず、規則の名前と件数だけを監査ログへ。同じ規則が週に何度も当たれば、伏せ字 1 の規則を足す |
| 公開の Issue に出てしまった | [漏れた時の手順](#漏れた時の手順) |

| LLM に送った文 | Anthropic | **要確認**。リポジトリにあるのはポリシー §1.3 の「同社の定める期間だけ保存して削除。違反の調査・法令の対応で長くなることがある」だけで、日数の記載は無い。学習に使われないことは商用の条件として書かれている。ゼロデータ保持(ZDR)を申し込めるかも要確認 | 取り消せない(送信済み)。ポリシーにそう書く(§1.3 と同じ) | — |
| 運営者のローカル | `cmd/feedback show -out` | 確認が済んだら消す(今の規則) | — | 手順に書いてある |
| ログ | Cloud Logging | 30 日。本文・伏せ字済みの文も書かない(ID と件数だけ) | 30 日で消える | 規則あり |
| バックアップ | Firestore | 最大 14 日 | 最大 14 日残る(§4 と同じ) | 設定済み |
| クラッシュ | Crashlytics | 90 日(Google の標準) | **伝わらない**(Crashlytics は uid で消す仕組みを今使っていない。消すかは要確認)。ループは件数しか持たないので、ループの側で消す物は無い | — |

その他:

- **論理削除中の人のフィードバックを流さない**。アカウントを削除した時点で `deletedAt` が付き、消去は 30 日後。段 1 は `users/{uid}.deletedAt` がある人のフィードバックを取り込まない。取り込み済みの写しも、次の段に進めない。
- **派生物は元より長く残さない**。元が 180 日で消えたのに、写しや振り分けの結果が残ると、ポリシーの「180 日で消去」を破る。TTL を元の `createdAt` から計算する。
- **GitHub Actions には何も残らない**(#365: フィードバックを Actions に通さない。エージェントは承認された Issue の本文だけを読む)。

## 漏れた時の手順

公開の Issue・コメントに個人情報が出たと気づいた時(下書きを非公開にしても、人の見落としはありうる)。

1. その段を停止スイッチで止める(`LOOP_DRAFT` など・#365)。
2. GitHub で該当の Issue・コメントを編集して消し、**編集の履歴の古い版も消す**(履歴の版は誰でも見られる)。必要なら Issue ごと消す(admin の権限が要る)。
3. 通知のメールで届いた分は取り消せないことを前提に、影響を記録する(何が・いつから・何人に見えたか)。
4. 本人への連絡と、個人情報保護委員会への報告が要るかを判断する(要配慮個人情報(健康など)の漏えいは件数によらず報告の対象になりうる。**要確認**)。
5. 原因の規則を伏せ字 1・検査器 2 に足し、試験の例を足してから再開する。
