## 結論(推奨)

**M0 では「お金のやり取りはアプリの外でする」までにする(案 B)。** 生成アプリに置けるのは「外部のページ・アプリを開くボタン」と「金額や支払い済みの記録」だけで、Tailor It の中でお金を動かさない。

- 今の `openUrlButton`(https と許可リストのスキーム)で、作者が自分で作った支払い用のリンク(PayPay の請求リンク・お店の EC ページなど)を置ける。**コードの変更は要らない見込み**(PayPay のリンクの形式は未確認。下の「根拠 3」)。
- `paypay://` のようなスキームを許可リストに足すのは、**PayPay が公開している仕様を確かめられるまで見送る**(今回の調査では公式の記載を見つけられなかった)。
- 生成アプリの「有料の機能・中身を解放する」ための支払いは作らせない(審査 3.1.1)。AI がそう作ろうとしたら断る文言をプロンプトに入れる(別 Issue)。
- 本格的な決済(Tailor It が加盟店になる・作者ごとに加盟店を束ねる)は、**資金の流れと法務の確認が要るので M4 以降に再検討**。

## 根拠

### 1. App Store 審査(2026-10-28 時点の本文)

- **3.1.1**: アプリ内の機能・中身を解放するには App 内課金が必須。「ライセンスキー・QR コード」等の独自の解放手段も不可。→ 生成アプリで「PayPay で払ったら有料の画面が開く」は不可。
- **3.1.3(e)**: アプリの外で消費する**実物の商品・サービス**の購入は、App 内課金**以外**の方法(例: Apple Pay・クレジットカード入力)を使わなければならない。→ 駐車場代・ガソリン代・お店の商品はこちら。
- **3.1.3(d)**: 2 人の間のリアルタイムのサービス(家庭教師・診察など)は App 内課金以外でもよい。1 対多は App 内課金。
- **3.2.1(vii)**: 個人から個人への金銭の贈与は、(a) 完全に任意で (b) 全額が受け取る人に渡るなら App 内課金なしでよい。ただしデジタルの中身・サービスと結びつく贈与は App 内課金。→ 「割り勘の送金」はこれに近いが、Tailor It 自身はお金を扱わず PayPay のアプリに渡すだけ、という形が一番安全。
- **3.2.1(viii)**: 金融取引・資金管理のアプリは、その業務をする金融機関が出すこと。→ Tailor It がお金を預かる・送る仕組み(案 C〜E)を持つと、この線に近づく。
- 審査で見られるのは Tailor It 本体。生成アプリで起きることも Tailor It の責任として見られる(`docs/store/app-review-notes.md` の 2.5.2・4.7 の説明と同じ考え方)。
- 補足: 日本の「スマホ新法」に合わせて、Apple は iOS 26.2 から日本のストアで App 内課金以外の決済(Alternative Payment Processing / Out-of-App Offers、手数料あり)を認めた。ただしこれは **Tailor It 自身のデジタル商品(Pro)の売り方**の話で、生成アプリの作者がお金を受け取れるようになる話ではない。Pro の売り方は #314・#326 で別に扱う。手数料の詳細は**要確認**。

### 2. PayPay for Developers(公式 API)

- オンライン決済(ウェブペイメント・アプリコール等)で PayPay を使うには、PayPay for Developers に登録して**加盟店の申し込み → 審査 → 本番用の ID 発行**が要る(PayPay の開発者向けヘルプ)。申し込み自体は無料と書かれている。
- 決済手数料・入金サイクル・審査に要る書類・「場を提供する事業者(プラットフォーム)が他人の代わりに使ってよいか」は、**今回の調査では公式の記載を確認できなかった(要確認)**。
- Issue に書いたとおり、生成アプリの作者ごとに加盟店契約をするのは現実的でない。

### 3. 契約なしでできること(PayPay の送金・請求)

- PayPay アプリには、個人間で使う**受け取りリンク**(送る側が作る。PayPay ヘルプでは作成から 96 時間で期限切れ)と、**請求リンク**(受け取る側が作り、LINE などで共有する)がある。
- これらを作るのは PayPay のアプリの中で、作るには本人確認が要る旨の案内がある。**リンクの URL の形式(https のユニバーサルリンクか、独自スキームか)と、請求リンクの有効期限は未確認**。
- **`paypay://` などの URL スキームで「送金の画面」を直接開く方法は、PayPay の公式ページでは見つけられなかった(未確認)**。非公式に動くスキームがあっても、仕様が変わると壊れるので、許可リストに入れるのは公式の記載か実機での確認が取れてからにする。
- 今の Tailor It でできること: `openUrlButton` は https を開ける(`ios/Packages/MetamonDSL/Sources/MetamonDSL/Model/ExternalLinks.swift` の `ExternalURLPolicy`、backend の `dsl.OpenURLSchemes`)。作者が PayPay で作った https のリンクをボタンに入れれば、押すと PayPay(か Web)に移る見込み。**実機での確認はまだ**。
- 案 B の注意: 請求リンクは期限や 1 回限りの可能性があるので、「固定のリンクを生成アプリに埋めっぱなし」が使えるかは実機で確かめる。使えなければ「PayPay を開く」ボタン + 「PayPay ID をコピー」程度に留める。

### 4. Apple Pay(実物・サービス)

- 3.1.3(e) で実物・サービスの支払いの例として Apple Pay が挙がっている。
- Apple Pay を使うには、アプリの開発者(= Tailor It)が Merchant ID を作り、決済代行(Stripe など)につなぐ形になる。お金は Tailor It の契約先に入るので、**誰が売り手か(Tailor It か作者か)を決めない限り使えない**(案 C・D と同じ問題)。
- 作者ごとに売り手にする(マーケットプレイス型)なら、本人確認・返金・紛争・資金決済法などの法務の確認が要る。**要確認**(法務・決済代行の両方)。

### 5. プロダクトの事情

- 起点は「運転中に使うアプリ」の例(駐車場代・ガソリン代・割り勘)。どれも実物・サービス・個人間なので、**お金そのものは PayPay のアプリでやってもらい、生成アプリは記録と導線だけ**で用は足りる。
- Tailor It 自身の課金(Pro・StoreKit)は別物。#77(RevenueCat の案)・#314〜#316・#326 で扱う。
- M4(サーバー機能の自動構築)で「他人の行動で通知」等が入ると、案 D(作者が売り手)の需要が出るかもしれない。その時に再検討する。
