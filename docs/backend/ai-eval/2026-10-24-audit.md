## 4. 上位 5 つの欠落と具体例

### 4.1 計算が無いのでユーザーに手計算させる(a)
a12 BMI(develop)。BMI が入力欄で、ラベルに計算式を書いて手計算させている。
```json
{"type":"numberField","field":"bmi","label":"BMI(体重÷2.89で計算)","placeholder":"例: 22.5"}
{"type":"text","text":"身長170cm・BMI = 体重 ÷ (1.7 × 1.7)","style":"caption"}
```
a03 シフト(develop)も同じ形: `勤務時間(終了-開始)` と `バイト代(時給1100円×勤務時間)` が numberField。式ブランチでは a12 は `bmi = round(weight / pow(1.7,2) * 10) / 10` の computed になった。

### 4.2 ラベルが嘘(b)
```json
{"type":"stat","label":"1人あたり","aggregate":"sum","field":"amount"}              // a01: 合計と同じ値
{"type":"stat","label":"予算の残り(3万円)","aggregate":"sum","field":"amount","filter":{"field":"date","op":"thisMonth"}}  // a17: 使った額
{"type":"chart","title":"種目ごとの自己ベスト(kg)","aggregate":"avg","groupBy":"exercise"}  // a06: 平均
{"type":"stat","label":"Points this week","filter":{"field":"date","op":"thisMonth"}}      // a20
{"type":"stat","label":"最新の体重(最小)","aggregate":"min","field":"weight"}              // a12
```

### 4.3 できない要求を黙って落とす(b)
a08 は「何日連続」を頼んだのに「筋トレ(日数)= 全期間の件数」で、summary は「習慣トラッカーアプリを作りました。今日と履歴の2タブで…」。代替を申告したのは 20 本中 a01 の「精算計算は、メンバー別の合計と平均で代替しました」だけ。今の規則は「カタログに無い**部品**」が対象で、計算・状態・期間には効いていない。

### 4.4 一覧からチェックできない(c → #108)
a14 買い物リスト。一覧は未購入/購入済で filter 済みなのに、チェックは「行タップ → フォーム → toggle → 保存 → 戻る」。6 本で同じ。式では埋まらない。

### 4.5 目標との差が出ない(a)
a10 は残額を固定文で出している: `"目標の100,000円まで、あと「100,000円 − 貯金合計」です。"`。式ブランチでは `max(100000 - sum(amount), 0)` の stat.value になった(a10/a11/a17/a19 の 4 本とも解消)。

## 5. 式ブランチ(#100)での改善幅と残る問題

`origin/feature/logic-expr-backend`(d112009)で同じ 20 本を 1 周(logic pass は off = 1 回の生成で式まで出す)。

| 指標 | develop | 式ブランチ |
|---|---|---|
| needs ○/△/× | 34/8/27 | 52/5/12 |
| 全部満たしたアプリ | 2/20 | 8/20(a01 a02 a05 a10 a12 a13 a16 a19) |
| 嘘ラベル | 7 | 2(a11 今年=全期間、a03 勤務時間が常に 0) |
| 平均出力トークン / create p50 | 1,173 tok / 6,414 ms | 1,248 tok / 6,381 ms(+6%・遅延はほぼ同じ・全ケース 1 回で通過) |

うまくいった例:
- a01 割り勘: `members.paid = sum(expenses.amount where payer == ref(id))`、`share = sum / count(members)`、`balance = round(paid - share)` + `settlement` 部品 + `payer: ref→members`。期待どおり。
- a06 ジム: `best = max(weight where exercise == ref(exercise))`、`is_pb = if(weight >= best, "🏆 ベスト更新", "—")`。
- a18 水やり: `next_watering = addDays(last_watered, interval_days)`、`days_left = daysUntil(...)`、一覧 filter `days_left <= 0`。

機械判定から手で直した点(ai-audit は「式があるか」までしか見ないので):
- **a03 は ○→×**: 勤務時間の式が意味をなさない。`round((toNumber(coalesce(end_time,"0")) * 0 + 0 - 0) / 1, 1)` = 常に 0。`start_time` / `end_time` は `"HH:mm"` 文字列で、時刻の差を取る関数が無いため Claude が辻褄合わせをした。検証は通る。バイト代と今月の合計も消えた。
- a15 / a20 順位: computed 合計で table を降順 sort → 並びは出るので ×→△(順位番号は無い)。a20 の今週は `addDays(today,-6)` の直近 7 日 → △。
- a08 連続日数: `streak = count(date in (date-7, date])` を「直近7日の記録数」と正直なラベルで出した。連続日数ではないので × のまま。

式ブランチで新しく出た問題:
- **entity が増えて行き止まりが出る**: a20 は `chores`(家事と点数のマスタ)を作ったのに追加フォームも一覧も無く、ログ側は点数を手入力(マスタが使われない)。a04 は `exam` の一覧が無い。lint `no_add_form` / `no_list` で検出できる。
- 代替の申告は 0/20 のまま(a03・a07・a08・a14 で黙って落とした)。

## 6. #100 担当向け: プロンプト/検証の改善案

プロンプト(`prompt.go` の設計原則 / 無い部品を求められたら):
- **ラベルは計算した中身どおりに書く**。「1人あたり」「残り」「平均」「最新」「自己ベスト」「今年」「今週」と書くなら、その値を本当に計算する(Expr で)。計算できないならラベルを実際の値(「合計」「全期間」)にする。例: 「予算の残り」= `sub(30000, sum(...thisMonth))`、「自己ベスト」= max(avg ではない)。
- **代替の申告を部品以外にも広げる**: 「発話の要求(計算・連続日数・順位・一括操作・タイマーの切り替え・期間)を DSL で表せない時は、近いもので代替して app.description の末尾に『○○は△△で代替しました。』と書く」。黙って落とさない。
- **計算をユーザーに入力させない**: 「○○を計算して」「○○を出して」と言われた値を numberField にしない・説明文(text)に式を書かない。computed / stat.value で出す。
- **人・メンバーは entity + ref**: 「誰が」「プレイヤー」「メンバー」「家族」が出たら、人の entity を作り(名前だけ)、記録側は `ref`。人ごとの合計は人 entity の computed `sum(... where person == ref(id))`、順位はその computed で table を desc sort。enum に「Aさん/Bさん」を固定しない。
- **目標との差は数値で**: 目標がある時は progressBar に加えて `stat.value = max(目標 - sum, 0)`。
- **時刻の差**: `"HH:mm"` 文字列同士の引き算はできない。勤務時間のように時刻差が要る時は datetime field 2 つ + 差の関数(無ければ「勤務時間」を入力にして代替を申告)。今の a03 のような意味の無い式を出さない。
- **作った entity は必ず使えるように**: entity を足したら、追加フォーム(toolbar の navigate)と一覧(list/table)を必ず置く。マスタを作ったら記録側から ref で使う。

検証(`pkg/dsl` の Validate・機械的に弾ける):
- `gt/gte/lt/lte` の filter で、date/datetime field に文字列リテラル(`"now"` 等)→ エラー(iOS は数値比較なので常に false = 一覧が空)。Expr(`{"op":"today"}`)なら OK。
- entity に追加フォームも一覧も無い → 警告として problems に載せて再生成。
- ラベル辞書(今月/今日/今年/今週/残り/あたり/平均/最新/ベスト)と filter/aggregate の不一致 → eval の assert(#87 の 1 番と同じ)。`cmd/ai-audit` の lint をそのまま流用できる。
- 定数倍が 0 になる式(`mul(x, 0)` など)は警告。

## 8. ai-audit の判定ルール

`backend/cmd/ai-audit/main.go`。DSL は `map[string]any` で緩く読むので、式ブランチの `computed` / `stat.value` / `settlement` / `ref` もそのまま判定できる。

| lint | 条件 |
|---|---|
| dead_button / bad_nav | action に type が無い / navigate 先の画面が無い |
| unreachable | initialScreen・tabs・navigate・saveRecord.screen のどこからも行けない画面 |
| no_save | `screen.entity` のフォームに saveRecord が無い |
| no_add_form / form_unreachable / no_list | entity の追加フォームが無い・行けない / 一覧(list/table/timeline/calendar/mapView/settlement)が無い |
| required_no_input / field_no_input | 必須 field に入力欄が無い / 入力欄の無い field(computed と日付は除く) |
| label_filter_mismatch / period_unsupported | ラベルに今月・今日があるのに filter(stat.value 内の filter も含む)が無い / 今週・今年(表す op が無い) |
| label_promises_calc | stat ラベルが「残り・あたり・順位・連続・BMI」等なのに単純集計 |
| static_value_text | text が計算値っぽい語 + 数字/記号を含む固定文 |
| toggle_invisible | toggle の field が一覧の filter / 表示に使われない |

`needs` の判定は `need()` の switch(部品・filter op・Expr の op の有無)。式が**正しいか**までは見ないので、§5 のように最後は人が DSL を読んで確認する。
