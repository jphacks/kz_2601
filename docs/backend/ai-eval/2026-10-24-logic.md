# ai eval: 計算ロジック(Expr)1 パス vs 2 パス(2026-10-24)

Issue #100。割り勘アプリで支出画面はできたのに「割る」計算が無かった問題への対応(仕様 [../../dsl/expressions.md](../../dsl/expressions.md))。
UI と計算を **1 回の生成で出す(1 パス)** か、**UI の後に計算だけを JSON Patch で足す 2 回目を呼ぶ(2 パス)** かを比べ、既定を決める。

```sh
cd backend
go run ./cmd/ai-eval -env-file ../.env -effort low -tag logic-1pass-final \
  -only logic_warikan,logic_bmi,logic_budget,logic_oshi,logic_countdown
go run ./cmd/ai-eval -env-file ../.env -effort low -tag logic-2pass-final -logic-pass \
  -only logic_warikan,logic_bmi,logic_budget,logic_oshi,logic_countdown
```

`-env-file` は KEY=VALUE を環境変数に読むだけ(値は出力しない)。生 JSON は `raw/2026-10-24-claude-sonnet-5-5-low-logic-*.json`。

## 1. 結論

**既定は 1 パス**(`AI_LOGIC_PASS` 未設定)。計算の出現率は両方 5/5 で同じ、1 パスの方が p50 で約 4 秒速く、出力トークンも少ない。
2 パスは `AI_LOGIC_PASS=1` / `Request.logicPass:true` で残す(計算カタログだけの小さなプロンプト・失敗しても 1 パス目を返す)。モデルを軽くしたい・UI の生成を先に返したい等で役に立つ可能性がある。

## 2. 結果(claude-sonnet-5-5・effort low・最終版コード)

| 指標 | 1 パス | 2 パス |
|---|---|---|
| 計算あり(computed / stat.value / settlement / progressBar target のいずれか) | **5/5** | **5/5** |
| expect 全達成 | 5/5 | 5/5 |
| 一発通過(再生成なし) | **5/5** | 4/5 |
| Claude ms p50 / p95 | **6,459 / 8,086** | 10,697 / 12,899 |
| 平均出力 tokens | **1,177** | 1,643 |
| 入力 tokens / 1 回目の呼び出し | 約 22.5K(キャッシュ対象) | 約 22.5K + 2 回目 約 4.3K |
| 2 回目の呼び出し | — | 全件 applied・2.2〜3.9s・出力 220〜530 tok |

ケース別(1 パス / 2 パス):

| id | 発話 | 1 パス: 生成された計算 | ms (1p / 2p) |
|---|---|---|---|
| logic_warikan | 旅行の割り勘アプリ。メンバーごとに誰がいくら払ったかと精算額が見たい | members.computed paid / share / balance・stat.value(1人あたり)・settlement・expenses.payer = ref | 8,086 / 11,222 |
| logic_bmi | 体重と身長を記録して BMI を出す | body.computed bmi(小数 1 桁) | 5,051 / 6,970 |
| logic_budget | 月の予算を決めて残りいくら使えるか見たい | stat.value = budget の max − 今月の expense 合計(budget entity で後から変更可) | 6,459 / 9,641 |
| logic_oshi | 推し活の目標金額に対して達成率 | stat.value = 貯金合計 ÷ 目標(percent) | 6,867 / 10,697 |
| logic_countdown | 試験日までのカウントダウン | exam.computed days_left = daysUntil(date)・stat.value = 最小の残り日数 | 4,788 / 12,899 |

計算の要らない既存ケース(kakeibo_a / training_a / walk_a / reading)も 1 パスで回し、**4/4 で computed / stat.value が付かない**こと(過剰生成なし)と expect 達成を確認(`raw/...-logic-1pass-r2.json`)。

## 3. 途中で直したこと(eval が見つけたもの)

| 発見 | 対応 |
|---|---|
| カウントダウンのレシピが `daysLeft`(camelCase)で id 規則違反 → 1 パス・2 パスとも再生成 1 回 | レシピを `days_left` に(`ba6e73f`) |
| 推し活で `progressBar.value` に式を書き、スキーマエラーが **120 行以上**(全 Leaf 型ぶんの type 不一致)返って再生成が重い | `flatten` が anyOf で「自分の type で落ちた分岐」を除き最深の分岐だけ返すように(1〜2 行に)。プロンプトに「式は computed / stat.value / agg filter.value だけ」を明記(`762fd81`) |
| 2 パスで 1 パス目に「計算は後で」と伝えると、stat を value も aggregate も無いまま出して再生成 | stat の文言を「entity+aggregate か value」の直し方つきに。2 パスは既定にしない理由の一つ |
| 初回(修正前)計測: 1 パス p50 6.5s / 2 パス p50 17.0s | 上の修正後の最終値が §2 |

## 4. 割り切り・注意

- n=5 × 1 回ずつの小さな比較。差(約 4 秒)は 2 回目の呼び出し 2〜4s とほぼ一致しており方向は安定しているが、精度の議論にはもっと回数が要る。
- 1 パスでも few-shot(例 3 = 割り勘)をほぼなぞる形で割り勘が出る。割り勘以外の「メンバーごとの集計」系(例: 部活の部費)は未計測。
- 評価(実際の数値)は iOS 側。backend は検証まで。iOS の評価器が §3 の op 一覧と同じ意味になっているかは iOS 側テストで担保する(#101)。
