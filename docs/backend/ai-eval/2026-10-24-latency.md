# ai eval: 生成の体感速度(Issue #61・backend 側)(2026-10-24)

create p50 6.1〜6.6s の内訳は「出力 1.2〜1.8K tokens の生成時間」がほぼ全て(effort / モデルでは縮まない・[2026-10-24.md](2026-10-24.md))。そこで **(1) 出力トークンを減らす**、**(2) 出力の先頭を先に iOS へ渡す(ストリーミング)** の 2 つを実装し、デモ 3 本+読書+水分の create 5 本 × 各 2 回で before / after を実測した。生 JSON は `raw/2026-10-24-claude-sonnet-5-5-low-latency-{before-1,before-2,after-1,after2-1,after-edit}.json`。

```sh
cd backend && set -a && source ../.env && set +a
go run ./cmd/ai-eval -effort low -only kakeibo_a,training_a,walk_a,reading,water -tag latency-before-1     # before(旧コード)
go run ./cmd/ai-eval -effort low -only kakeibo_a,training_a,walk_a,reading,water -tag latency-after-1 -stream   # after(SSE 経路・first event も計測)
go run ./cmd/ai-eval -compare-before 'raw/*-latency-before-*.json' -compare-after 'raw/*-latency-after*.json'   # API を呼ばず表だけ
```

API 呼び出し: before 10 + after 10 + edit 2 + `count_tokens` 2 = **24 回**。

## 2. 採用した施策

| # | 施策 | 実装 | 効果 |
|---|---|---|---|
| 1 | **compact JSON で出力させる**(改行・インデント無し) | `prompt.go` の「出力の書き方」節 + few-shot 2 本を `abbreviateExample()` で compact 化して埋め込む | **出力トークン削減の主因**。`count_tokens` 実測: 同じ家計簿 DSL が pretty 1,871 tokens → compact 1,287 tokens(**−31%**)。before の出力 1,582 tokens は一部改行入りだったと推定(after の `outputChars` は compact JSON 長とほぼ一致) |
| 2 | **既定値を書かせない → Go で補完** | `defaults.go` `fillDefaults`(create)/ `fillPatchDefaults`(edit の value)。schemaVersion / voiceEntry floating / navigate.presentation(フォームへは sheet・行タップは push)/ filter.value null / sort.direction desc / list.swipeToDelete true / stat・chart.aggregate sum / date の defaultValue now。`pkg/dsl` は不変(補完後に `dsl.Parse`)。`TestAbbreviateRoundTrip` が「例の省略形 → 補完 = 正典」を保証 | 出力 −5〜8%(1 アプリあたり 60〜100 tokens)。iOS には従来どおり明示値が届く |
| 3 | **ストリーミング + 先頭 `app` ブロックの先出し** | `client.go` が `stream: true` の SSE を読み `Completion.OnText` に逐次渡す。`stream.go` `keyWatcher` が深さ 1 の `app`(edit は `summary`)の完了を検出し `Event` を発火。`POST /v1/generate?stream=1` が `event: app` → `event: result` の SSE(`handler.go`)。create のキー順は app → initialScreen → entities → screens をプロンプトで指定 | **first event p50 2.4s**(完了 6.0s)。iOS は名前と「家計簿アプリを作っています。ホームと集計の2タブです。」を先に表示/読み上げできる。本体の DSL は従来どおり完了後に検証して `result` で送る |
| 4 | edit の PatchDocument を **summary 先行** `{"summary":…,"patch":[…]}` に | `editRules` + `summaryEventWatcher` | edit の読み上げ文が ops より先に届く(§4) |

体感の設計: 完了まで 6s のうち、2.4s で名前+仮要約、6s で画面。再生成が入ると `app` イベントは attempt を変えてもう一度届く(iOS は最新を採用)。

## 3. 不採用・見送り

| 案 | 判断 | 理由 |
|---|---|---|
| カタログ `x-usage` の 1 行要約・設計原則の重複削り | **見送り** | すでに 1 行/部品。system は全体キャッシュ済み(`cache_read_input_tokens=16,747`)で、入力側は TTFT にしか効かない。few-shot の compact 化だけで −560 tokens 取れたので、品質リスク(用途の説明が薄くなる)を取ってまで削らない |
| en few-shot を home 画面だけに短縮 | **見送り** | 入力 −0.8K の見込みに対し、en の create が form の型を失うリスク。25 回の予算で en の回帰を取れないため今回は触らない |
| 部品 `id` の省略 | **不採用** | 1 アプリ 40 tokens(3%)しか減らない割に、検証エラーメッセージ(`(id "recent")`)と編集時の可読性が落ちる |
| button.style primary / field.required の省略 | **不採用** | iOS 側の既定描画と一致する保証が無い(iOS は触らない前提) |
| effort / モデル変更 | 済み(前回) | low で固定。high は遅いだけ、Opus は +2.3s |
| 先読み(文字起こし途中で生成開始)・スケルトン予想描画 | iOS 側 | backend は `app` イベントで名前/タブ名を先に渡すので、スケルトンにタブ名を先に描ける |

前回(catalog eval)の同 2 本は 1,573 / 1,552 ms。summary 先行+compact 指示で edit も 1 発通過のまま、読み上げ文は **約 1s** で届く(完了 1.3〜1.4s)。

summary が先頭にあるので ops より前に届く。value の省略形(presentation 等)が出ても `fillPatchDefaults` が補完してから `dsl.ApplyPatch` に渡す。

## 5. 観測メモ

- **トークン削減ほど時間は縮まない**: 出力 −26% に対し p50 −8%。pretty JSON の改行・インデントは予測しやすく 1 トークンあたりの生成が速かった(投機的デコード)と考えられ、compact 化で「1 トークンの重さ」が増えた。それでも wall-clock は全ケースで短縮(外れ値 1 本を除く)し、first event で体感は大きく変わる。
- **TTFT のばらつき**: first event は 1.8〜3.1s が通常、1 本だけ 8.9s。API 側の stall なので backend では吸収できない。iOS 側は first event が 4s を超えたら「もう少しかかります」を出す閾値に使える。
- 入力は 16.9K tokens(キャッシュ)で、user ターンは 120〜160 tokens。キャッシュ作成は最初の 1 回だけ(`cache_creation_input_tokens=16,747`)。

## 6. iOS 側の残作業(別 Issue)

1. `POST /v1/generate?stream=1` を `URLSession` の bytes ストリームで読み、`event: app` の `name` / `tabs` / `summary` をスケルトンに即描画+読み上げ、`event: result` で DSL を適用(`event: error` は従来のエラー処理)。
2. 既存の JSON モードは残る(`stream` 無し)。SSE が失敗したら JSON モードへフォールバックしてよい。
3. edit は `event: summary` が先に来るので、「カテゴリにカフェを追加しました。」を読み上げ始めてから `result` を適用できる。
4. 生成中表示の目安: first event 2〜3s(超えたら「考え中」)、完了 5〜8s。
