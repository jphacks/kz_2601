# ai 生成品質・速度 eval(2026-10-24)

発話 16 本(`backend/internal/ai/eval/cases.json`)を `backend/cmd/ai-eval` で実 Claude API に流し、`dsl.Parse` 通過・再生成・フォールバック・レイテンシ・レイアウトを計測した。生 JSON(結果 DSL 込み)は `raw/`。

```sh
cd backend && set -a && source ../.env && set +a
go run ./cmd/ai-eval -effort low -model claude-sonnet-5-5 -tag <label>   # 16 本
go run ./cmd/ai-eval -effort low -only kakeibo_a,edit_cafe                # 一部だけ
```

- create 10 本: デモ3本の言い換え各 2(家計簿は 1 本が「家計簿」だけの短い発話)+ 読書記録 / 水分 / 買い物リスト / 体重
- edit 6 本: 同一ランの `kakeibo_a` の結果を基底に独立に適用(カフェ追加 / 合計を大きく / グラフを消す / 毎晩 9 時通知 / 一覧を写真付き / ボタンを左上)
- ランナーは HTTP を介さず `ai.Service` + インメモリ store を直接叩く(ハンドラと同じ経路)。API 呼び出し合計 54 回(baseline 32 + 改善後 16 + Opus 3 + 再確認 2 + 再生成 1)

## 4. デモ3本の安定性

言い換え 6 本(kakeibo_a / 「家計簿」 / training_a / training_b / walk_a / walk_b)は low・high・改善後 low の全 18 回で検証一発通過・フォールバック無し。筋トレ 2 本は毎回 `app.notifications` daily 08:00 が入り、散歩 2 本は毎回 `photoField`(camera)が form に入り、家計簿 2 本は `receipt: photo` + 円グラフ(要求時)が入った。「家計簿」だけの発話でも金額・カテゴリ・メモ・日付・レシート写真の 5 field が出る(few-shot の恩恵)。

## 5. 残リスクと iOS への提案

- **p95 の長尾**: high の walk_a が 17s(2,838 tokens・見返し画面に list 2 枚)。low でも 1,700 tokens 級(training_a 8.7s)は出る。出力長に比例するので、発話が長く要素が多いほど遅い。
- **崩れうる発話**: 複数アプリの混在(「家計簿と筋トレ両方」)・entity 3 つ以上の要求・「グラフを 5 種類」など部品 30 超を誘う指示・既存 DSL と矛盾する edit(存在しない部品への言及)。今回の 16 本には入れていない(次回の eval 候補)。
- **edit の over-reach**: 「グラフを消して」で画面ごと消える挙動はルール化したが、ユーザーが「タブは残して」と思う可能性はある。デモでは「集計タブごと消えます」と言える summary になっている。
- **chart は iOS P1**: 要求時のみ出すようにしたが、家計簿デモ A は 内訳要求を含むので chart が出る。iOS 側のプレースホルダ描画が前提。
- **iOS 生成中表示の目安**: create は **5〜9 秒(p50 6.6s・p95 8.7s)**、edit は **1〜4 秒(p50 1.7s・p95 5s)**。「生成中」は 10 秒まで通常表示、10〜20 秒で「もう少しかかっています」、再生成が入ると +7s 程度(1 回分)なので警告 20s / フォールバック 30s の既存設計(01 §4)と整合する。create 中は summary が「右下のボタンから◯◯を追加できます」と案内するので、反映直後にその位置をハイライトすると効果的。
