## 今の形(事実)

- **文字・画像・URL を共有で受ける口は、どの OS にも無い**。iOS に Share Extension は無い(`ios/` の拡張はウィジェットだけ・`NSExtension` は `MetamonWidget`・`MetamonMacWidget` の 2 つ)。Android の `AndroidManifest.xml` に `ACTION_SEND` の `intent-filter` は無い。デスクトップに OS から渡される物を受ける口は引数(下)だけ。
- 外から受けているのは**リンクだけ**: `tailorit://import/<token>`・`https://tailor-it.app/s/<token>`(共有されたアプリを開く物)。iOS・Mac は `onOpenURL`、Android は `intent-filter` の VIEW([`MacLinkReceiver.swift`](../../ios/MetamonMac/App/Links/MacLinkReceiver.swift)・[`AndroidManifest.xml`](../../android/app/src/main/AndroidManifest.xml))。知らない URL は何もしない。
- デスクトップは 2 つ目の起動を、起動中の方へ引数ごと引き継ぐ([`SingleInstance.kt`](../../desktop/app/src/main/kotlin/jp/kz2601/metamon/desktop/SingleInstance.kt)・`main(args)`)。「ファイルを Tailor It で開く」の受け口を作る時の土台になる(**推測**: 引数の最初はアプリの定義の指定に使われているので、渡し方の規約を決める必要がある)。
- 取り込みの部品は既にある: `fileImport`(csv / text / pdf / audio をファイルから記録に取り込む・端末内で処理・足す前に件数を確かめる)。`textField`・`photoField` などの欄は、フォームの入力として値を持つ([`docs/dsl/README.md`](../dsl/README.md) の「ファイルの取り込み」)。
- 「どのアプリのどの欄に入れるか」を表す DSL の欄は無い。アプリは複数ある(1 人が生成アプリを複数持つ)。

## やりたいこと

- ブラウザで見ているページの URL、メモアプリの文、写真アプリの 1 枚を「共有 → Tailor It」で渡すと、いずれかの生成アプリの記録(の欄)に入る。
- 何を受けたか(文字・画像・URL)が分かる範囲で、行き先が自然に決まる。迷う時は聞く。

## 案

### 案 A: 毎回聞く

共有を受けたら、アプリの一覧(と、そのアプリの入れられる欄)を出してユーザーが選ぶ。選んだ後に、記録の入力フォームが埋まった状態で開く。

### 案 B: 最後に使ったアプリに入れる(確認の画面は出す)

直近で共有を受けたアプリを先頭に出し、「ここに入れる」を 1 タップにする。他のアプリを選ぶこともできる。

### 案 C: 種類で決める(アプリ側が「受けられる物」を宣言する)

各アプリの DSL に「受け口」を書いておく(例: `app.shareTargets: [{ accept: "url", entity: "bookmarks", field: "link" }]`)。受けた物の種類(文字・画像・URL)と合う受け口を持つアプリだけを候補にする。候補が 1 つなら自動、複数なら案 A。

(形の例。名前は仮・**決めること**)

## 案の比較

| 案 | 良い点 | 困る点 | 互換・検証 |
|---|---|---|---|
| A: 毎回聞く | 一番分かりやすい・間違って別のアプリに入りにくい。DSL を変えなくても始められる(アプリの全部の一覧から選ぶ) | 毎回 1 手間かかる。アプリの数が多いと探しにくい。入れられる欄が無いアプリも並ぶ | 新しい DSL 無し(**推測**)。iOS の Share Extension は別プロセスなので、アプリの一覧・欄の情報をアプリと共有する置き場(App Group)が要る |
| B: 最後に使ったアプリ | 同じ使い方が続く時に速い。A に足せる | 「最後」が別の目的のアプリだと、意図しない所に入りやすい(確認の画面で防ぐ前提)。端末ごとの記憶になる(別の端末とは揃わない) | 保存場所は端末の中。DSL 変更なし |
| C: 種類で決める | AI が生成する時に受け口も書ける。候補が絞れて速い。「URL は ブックマークのアプリ」のような規則が持てる | DSL に欄を足す(決定事項の変更・AI のカタログ・検証が増える)。古い版は受け口を無視する(落ちはしない・**推測**)。既存のアプリには受け口が無い | Go に「受け口の entity・field が在り、種類に合う型か」を検証する関数が要る。`accept` の語は閉じた一覧にする |

## OS ごとの受け口

| OS | 受け口 | 受けられる物 | 作れるか | 注意 |
|---|---|---|---|---|
| iOS | Share Extension(新しい拡張ターゲット) | 文字・URL・画像(`NSExtensionActivationRule` で種類を指定) | ○ 作れる(**推測**) | 拡張は別プロセスでメモリの上限が小さい(**推測**)。アプリの一覧は App Group 経由で読む。審査・entitlement・ビルドの設定は人の作業。拡張から本体を開く渡し方(URL スキーム・共有の置き場)を決める必要 |
| Mac | Share Extension(macOS 版)または「サービス」メニュー | 文字・URL・ファイル | ○ 作れる(**推測**) | iOS と同じ設計を共有できるか(`ios/Shared/` の使い回し)は未確認 |
| Android | `MainActivity` に `ACTION_SEND` / `ACTION_SEND_MULTIPLE` の `intent-filter` | 文字(`text/plain`)・画像(`image/*`)・URL(文字として) | ○ 作れる(**推測**) | 共有メニューに「Tailor It」が出る。受けた画像は `content://` の一時的な許可で渡るので、取り込んで縮小してから使う。今の `MainActivity` は `singleTask` なので、開いている時の渡り方に注意 |
| デスクトップ | 「Tailor It で開く」(ファイルの関連付け)・コマンドの引数・貼り付け | ファイル(画像・テキスト・PDF など)。URL・文字は貼り付けか `fileImport` のドラッグ | △ ファイルだけ現実的(**推測**) | `SingleInstance` が 2 つ目の起動の引数を渡す。URL・文字を OS の共有メニューから受ける口は標準では無い(**推測**) |

## 決めること

- 案 A / B / C のどれか(あるいは A から始めて C を足す、のような順序)。
- 受けた物が別の人に見える場所(`scope: shared / public` の entity)へ入る時に、確認を必ず挟むか。
- 画像・長い文字の上限(`photoField` の縮小と同じ規則でよいか)。受けた URL の中身(ページの題名など)を取りに行くか(取らない案もある)。
- 受けた物を一度に複数(複数の画像)受けるか。
- デスクトップは「ファイルで開く」だけでよいか(URL・文字は貼り付け)。
- iOS・Mac の拡張ターゲットを足すこと自体(審査・ビルド設定・entitlement は人の作業)。
- `supportedFeatures`(機能の申告)のキー名(#1775 の判断待ち)。
