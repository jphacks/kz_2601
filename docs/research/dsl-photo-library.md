## 今の形(事実)

- 写真は `photoField`(カメラか、写真から**選ぶ**)で記録の欄に入れる。選ぶのは `PhotosPicker`(OS の選択画面)で、アプリはライブラリ全体を読まない(`PhotoSourcePolicy`・[`PhotoSourcePolicy.swift`](../../ios/Packages/MetamonRenderer/Sources/MetamonRenderer/Support/PhotoSourcePolicy.swift))。値は縮小した JPEG の data URL か https の URL([`docs/dsl/README.md`](../dsl/README.md) の決定表 14)。
- ライブラリへ**書く**のは `addOnly` の許可だけ(QR の保存・ドライブレコーダーの書き出し。`PHPhotoLibrary.requestAuthorization(for: .addOnly)`)。**日付でライブラリを読む口は無い**(`PHAsset` の取得・`creationDate` での検索を `epic/god` で grep しても 0 件。Android は `MediaStore`・`READ_MEDIA_IMAGES` も 0 件)。
- 写真を持つ部品は `image`(写真の欄を表示)・`photoField` など。共有・公開の entity の記録は他の人にも見える。`scope: shared / public` の記録の扱いは [`docs/dsl/README.md`](../dsl/README.md) の「entity.scope」の節。`profile` の entity は photo / video の欄を持てない、という既存の規則もある。
- デスクトップに写真ライブラリを読む口は無い(`PHAsset` 相当のコードなし)。写真の欄は `PhotoPreview.kt`・`ImageLoader.kt` で扱っている。写真を入れる操作の細部は未確認(**推測**: ファイルを選ぶ形)。

## やりたいこと

- 「この日の写真」を、記録(日記・食事・散歩)の横に**表示**する。または日記に**添える**(記録に取り込む)。
- 写真は端末の中にあるままで、ユーザーが選んだ物だけが記録に入ること。

## 案

### 案 A: 表示だけの部品 `photosOfDay`(読むだけ・記録には入れない)

記録の日付の欄を指定すると、その日の写真のサムネイルを一列に出す。写真のデータは端末の中のメモリだけ。`image` と同じく「表示専用の Leaf」。

### 案 B: 日付で絞った選択画面を開くボタン(選んだ物だけ記録に入れる)

ボタンを押すと、OS の選択画面を「この日」の写真に絞って開く。ユーザーが選んだ物が `photoField` と同じ形で記録に入る。ライブラリ全体の許可は要らない(選択画面経由・**推測**)。

### 案 C: 許可をもらってライブラリを日付で読み、取り込みを一括で提案する

「この日の写真 12 枚を日記に添えますか」と提案する。ライブラリの読み取り許可(全部か一部)が要る。

## 案の比較

| 案 | 良い点 | 困る点 | 互換・検証 |
|---|---|---|---|
| A: 表示だけ | 記録に入らないので、共有・同期・公開に写真が流れない(**推測**・実装次第)。審査の説明がしやすい | 読む許可が要る(全部か一部)。一部だけ許可の時、その日の写真が少なく見える | 新しい Leaf。未知 type は古い版でプレースホルダ。`screen.entity` に日付の欄が要る検証を足す |
| B: 絞った選択画面 | 今の `photoField` の流れに近い。許可を新しく取らずに済む可能性(**推測**) | OS の選択画面は日付で絞る指定が限られる(**推測・要確認**)。絞れないなら「全部から選ぶ」と同じ | `photoField` に `date` の絞りを足す形でも書ける(別 type にしない案) |
| C: 一括の提案 | 手間が最も少ない | 許可の範囲が一番広い。共有のアプリへ誤って流れる心配が最も大きい。提案の言い方を誤ると、見せるつもりのない写真が記録に入る | 許可の説明文・審査の説明・プライバシーの表示の更新が要る(人の作業) |

## OS ごとにできるか

| OS | 日付でライブラリを読む | 選択画面を日付で絞る | 根拠・注意 |
|---|---|---|---|
| iOS | ○ 作れる(**推測**) | △ OS の選択画面の指定に依る(**推測・要確認**) | `PHPhotoLibrary`・`PHAsset` の `creationDate` で検索できる。許可は全部・一部・なしの 3 状態(一部は選んだ分だけ見える) |
| Mac | ○ 作れる(**推測**) | △ | 同じ API が在る(**推測**)。使う理由の文言の更新が要る(`ios/scripts/strip-review-plist.sh` は審査用の版で写真の許可の文言を差し替える。読む許可を足す時の扱いは **決めること**) |
| Android | ○ 作れる(**推測**) | △ | `MediaStore` を日付で問い合わせる。13 以降は `READ_MEDIA_IMAGES`、14 以降は一部だけの許可(選んだ写真だけ)がある |
| デスクトップ | △ フォルダを指定して読む形なら(**推測**) | × | 写真のライブラリという概念が無い。指定フォルダの更新日・撮影日(EXIF)で代える形になる(**決めること**) |

## 注意: 一部だけの許可と、共有のアプリ

| 場面 | 起きること | 案に入れる扱い(**決めること**) |
|---|---|---|
| 一部だけ許可 | ユーザーが選んだ写真しか見えない。その日の写真が「無い」ように見える | 「一部だけ許可されています」と出し、許可の変更へ誘導する。「写真が無い日」と混ぜない |
| 共有のアプリ(`scope: shared / public` の entity) | 記録に入った写真は参加者・公開の閲覧者にも見える | ライブラリから読んだ写真は、**ユーザーが 1 枚ずつ選んで記録に入れた時だけ**その記録の欄に入る。表示だけの部品は共有・同期・書き出し・AI への送信の対象にしない |
| 共有のアプリの画面にある `photosOfDay` | 画面を見ている人は自分だけだが、画面のスクリーンショット・画面の共有で他人に見える | 画面に出す写真の数・大きさに上限を付ける(**決めること**)。他人の端末には写真のデータを送らない |
| AI に見せる(`aiButton.inputPhoto`) | 写真をオンライン AI に送る機能が既にある(プライバシーポリシーが書くまで本番で使えない・[`jphacks-coverage.md`](jphacks-coverage.md) の記述) | ライブラリから読んだ写真を AI に渡す経路は作らない前提でよいか(**決めること**) |
| 位置・撮影日の情報 | 写真の EXIF に場所が入っていることがある | 取り込む時に位置情報を落とすか(**決めること**) |
