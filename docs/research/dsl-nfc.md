## 今の形(事実)

- **NFC を使うコードはどの OS にも無い**(`CoreNFC`・`NfcAdapter`・`android.nfc` を `epic/god` で grep しても 0 件。`AndroidManifest.xml` にも NFC の記述なし)。
- アプリを外から開く口は既にある: URL スキーム `tailorit://import/<token>`(iOS・Mac は `onOpenURL`・Android は `intent-filter` の VIEW)と、`https://tailor-it.app/s/<token>`(Universal Links・App Links)。`<token>` は共有リンクの物([`AndroidManifest.xml`](../../android/app/src/main/AndroidManifest.xml)・[`MacLinkReceiver.swift`](../../ios/MetamonMac/App/Links/MacLinkReceiver.swift))。
- DSL のアクションは閉じた一覧(`ActionType`・16 種・[`dsl.go`](../../backend/pkg/dsl/dsl.go))。`saveRecord`・`navigate` などで、NFC に当たる物は無い。自由な文字列の `feature` は採らない決定がある([`docs/dsl/README.md`](../dsl/README.md) の決定表 17)。
- Issue の本文では、iOS に「読み書きの口」、Android に「読む口」の土台を別 Issue で作る前提。中身は未確認。

## やりたいこと

- 机や冷蔵庫に貼ったタグにスマホを近づけると、決まった記録が 1 件足される(例: 「ジムに着いた」)、または決まった画面が開く。
- タグは安い汎用の NDEF タグ(自分で書き込める物)で足りること。専用の機器を要求しない。

## 案

### 案 A: タグに「アプリを開く URL」だけを書く(既存のリンクの口を使う)

タグには `tailorit://…` か `https://tailor-it.app/…` の URL を NDEF で書く。OS がその URL を開く。DSL 側は、その URL が開いた時に実行する物を `app` の宣言に持つ。

```json
{ "app": { "tags": [ { "id": "gym", "label": "ジム", "action": { "type": "saveRecord", "entity": "visit" } } ] } }
```

(形の例。名前は仮・**決めること**。URL は `.../tag/<appId>/<tagId>` のように、タグの id だけを運ぶ)

### 案 B: アプリの中で「タグを読む」ボタン(Leaf)を置き、読んだ値を欄に入れる

画面に `nfcReader` のような部品を置く。押すとタグを読み、値(文字や id)をフォームの欄に入れる。記録は今ある `saveRecord` で行う。

### 案 C: A と B の両方(外から開く物は A・アプリ内の読み取りは B)

## 案の比較

| 案 | 良い点 | 困る点 | 互換・検証 |
|---|---|---|---|
| A: URL を書いたタグ | 既存のリンクの口(`onOpenURL`・Android の VIEW)の上に載る。スマホのロック中・アプリ未起動でも OS が開く(**推測**)。タグの書き込みは OS 標準の NDEF で足りる | タグの id の付け方と、同じ形の URL を受けた時の扱いを決める必要がある(**決めること**)。アプリ未導入の人はウェブに飛ぶ | 新しい URL の形を足す(決まったリンクの規約に触る)。DSL の検証は「タグの id が `app.tags` にあるか」 |
| B: 読むボタン | 使う側が「今これで読む」と分かる。何を読むかを画面で絞れる(読んだ値を欄に入れるだけ) | 画面を開いてから当てる 2 手になる。`Leaf` の追加は iOS・Android・デスクトップのレンダラーに表示のしかたが要る | 未知 type は iOS がプレースホルダにするので古い版は落ちない |
| C: 両方 | 目的別に使い分けられる | 作る物が増える。AI の決まり(カタログ)が増える | A と B の合計 |

## OS ごとにできるか

| OS | 読む | 書く(タグへ) | 外から開く(アプリ未起動) | 根拠・注意 |
|---|---|---|---|---|
| iOS | ○ 作れる(**推測**) | ○ 作れる(**推測**) | ○ 条件つき(**推測**) | Core NFC(`NFCNDEFReaderSession`)。entitlement と使う理由の文言が要る。対応機種のみ。背景読み取りは URL の NDEF に限られる(推測) |
| Android | ○ 作れる(**推測**) | ○ 作れる(**推測**) | ○ 作れる(**推測**) | `NfcAdapter` と `intent-filter` の `NDEF_DISCOVERED`。NFC が付いていない機種・設定で切ってある機種がある |
| Mac | × 作れない(**推測**) | × | △ タグを読めた別の端末から URL を渡す形なら | Mac の標準の API に NFC のタグの読み取りが無い(推測・要確認) |
| デスクトップ(JVM) | △ USB の読み取り機がある時だけ(**推測**) | △ 同上 | × | 標準では NFC が無い。専用の機器を要求する形は採らない前提なら × 扱いが妥当(**決めること**) |

## NFC の無い端末での見え方

- 案 A: NFC の無い端末ではタグの URL を**手で開く**代わりの物が要る。例として、同じ URL の QR コード(`QrCodeLeaf` が既にある)を画面に出す・ボタンで同じ記録を足す。タグの代わりの手段を 1 つ必ず付けるかは **決めること**。
- 案 B: 部品は NFC の無い端末では「この端末では使えません」の表示にして、フォームの欄を手で埋められるようにする(**推測**・既存の「使えない」の見せ方(適合テストの `edge-unknown-and-unavailable`)に合わせる案)。
- どの案でも、`supportedFeatures`(機能の申告)に NFC のキーを足して、AI が NFC 前提のアプリを NFC の無い端末向けに作らないようにする話は、#1775 の判断待ち。

## 決めること

- 案 A / B / C のどれか(あるいは別案)。
- タグに書く内容(URL だけか・アプリ id と操作の id か)と、同じ形の URL を受けた時の扱い。
- NFC の無い端末・Mac・デスクトップでの代わり(QR・ボタン)を必須にするか。
- iOS の entitlement・使う理由の文言(審査の説明に関わるので人が決める)。
- `supportedFeatures` のキー名(#1775 の判断待ち)。
